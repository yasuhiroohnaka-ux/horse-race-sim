## 2. 致命的な問題

### A. 払戻をスナップショットオッズ×100 で計算している（すべての誤りの根源）

監査は「47.8倍 → 4,780円」のように、**事前スナップショットのオッズをそのまま払戻として扱っている**。実際の公式単勝払戻と比べると：

| レース | 馬名 | snapshot odds | 監査の払戻 | **公式払戻** |
| :--- | :--- | ---: | ---: | ---: |
| 202605030309 | インペリアルライン | 47.8 | 4,780 | **1,150** |
| 202604010310 | スピンザブラッド | 23.6 | 2,360 | **720** |
| 202607010211 | シェイクユアハート | 13.8 | 1,380 | **1,350** |
| 202605030110 | ロジケープ | 13.0 | 1,300 | **1,120** |
| 202605020209 | カンシン | 12.9 | 1,290 | **900** |
| 202606020711 | スマートプリエール | 12.8 | 1,280 | **1,280** |
| | **合計** | | **12,390** | **6,520（52.6%）** |

全体でも、確定本命の単勝的中 103 件で `公式払戻 / スナップショットオッズ` は **平均 0.919 / 中央値 0.879**、71/103 件でオッズが縮んでいる。穴馬帯ほど乖離が大きい。

この一点だけで監査の結論が反転する：

| 指標 | スナップショットオッズ採点（監査の方法） | **公式払戻採点** |
| :--- | ---: | ---: |
| シミュレータ rank1 ベタ買い | 115.2% | **85.6%** |
| 同 オッズ 10〜20倍帯 | 192.5% | 183.0% |
| 同 オッズ 20倍以上帯 | 193.0% | **50.5%** |

「§1(2) 重大なブレイクスルー」の 114.5% は、**公式払戻で採点すると 85.6%**（95%CI [60.6, 112.9]）。ブレイクスルーは存在しない。

### B. 「114.1%」は v3.0 の数字ではなく rank1 オラクルの数字

シミュレータ rank1 ベタ買いをスナップショットオッズで採点すると **115.2% / 的中17.5%**。監査の「新モデル 全体ベタ買い 114.1% / 的中17.1%」とほぼ一致する。
つまり §0 の表の「新モデル」列は、**選定層を通した v3.0 の実績ではなく、rankedRows rank1 をそのまま買った場合の数字**が入っている。実際の v3.0 は 81.2%（公式払戻）／87.4%（スナップショット採点）。

### C. §3(1) の実例表は、記載どおりには検証できない

6 行すべてで raceId が実データと一致しない。うち 3 件（202604010301 / 202609020406 / 202605020108）は `review-records.json` にも `weekly-races.json` にも存在しない。

- `202604010609`: 監査は「インペリアルラインが 47.8倍で1着」。実際の勝ち馬は **ラヴェンデル**、v2.5 の本命は **ダノンゴーイチ（4.1倍・不的中）** であって「ビービーアジャイル（1.1倍・2着）」ではない。インペリアルラインが 47.8倍で勝ったのは **202605030309**。
- `202605020210`: 監査は「旧本命 コートアリシアン 3.3倍 5着」。実際のその日の本命は **ドンインザムード 3.5倍で的中（払戻290円）**。カンシンが 12.9倍で勝ったのは **202605020209**。
- `202605020110`: 旧本命は **メイショウハチロー 3.0倍**（イクシード 2.7倍 3着ではない）。スマートプリエールの 12.8倍勝ちは **202606020711**。

馬名とオッズ自体は実在のデータ（rank1 で勝った馬）なので、捏造というより **レースID と旧本命列の突き合わせを行わずに表を組み立てた**ものと見える。いずれにせよ、この表は「v3.0 が獲得した」ことの証拠にならない。旧本命が的中していたレースを「旧本命は負けていた」と記載している行がある点は特に問題。

### D. 「改変前」列が汚染されている

§0 の「旧モデル class win = 89.8%（n=87）」は、**再生成後の `calibration-report.md` の行そのもの**、すなわち「**新ゲート × 旧picks**」の数字である。HEAD の v2.4 ゲートでの実際の値は **119.1%（n=34）**。

同一 picks でゲートだけを比較すると、変化は **119.1% → 89.8%（−29.3pt）**。監査が「+37.4pt」としているのは、劣化した数値をベースラインに据えた結果。

### E. リポジトリ自身の out-of-sample スライスは、すべて新ゲートの劣化を示している

再生成された `calibration-report.md`（新ゲート × 旧picks）を HEAD と比較：

| スライス | v2.4 ゲート | **v3.0 ゲート** |
| :--- | ---: | ---: |
| 事後 holdout 96件 class win | 163.3%（n=3） | **46.5%（n=23）** |
| 後半 out-of-sample class win | 113.1%（n=16） | **61.3%（n=40）** |
| 直近50件 class win | 163.3%（n=3） | **61.5%（n=13）** |

旧側の n が小さく単独では弱い証拠だが、3 つの独立スライスで方向が揃っている。監査はこのレポートを自分で再生成しておきながら、この結果に触れていない。

### F. 「OOS で110%超を実証」は成立しない

確定済みレースに対して選定をやり直したものは、定義上すべて in-sample。`live_pre_race` は**スナップショットの取得タイミング**を示すフラグであって、予想の作成タイミングではない。
しきい値（3.5倍 / ROI 108 / 勝率0.12 / 25.0倍 / ボーナス0.03 / 重み 0.75:0.25）はすべてこの 327 レースを見ながら選ばれている。

### G. 検出力が足りない

rank1 ベタ買い（公式払戻）の 95% ブートストラップCI は **[60.6%, 112.9%]**。n=333・的中17% では 10pt のエッジは判別できない。監査が根拠にした「20倍以上帯 193%」は **的中 2 本**、公式払戻では 50.5%、CI [0, 132]。

### H. §2(2) の skip ゲート説明は、存在しないコードを記述している

監査は「skip ゲートを刷新した」として次を挙げる：
- 「過熱見送り: 単勝2.5倍未満で期待値85%未満」
- 「混戦見送り: 校正勝率10%未満の大混戦」

実際の `classifyHonmeiPick` の skip 条件は **v2.4 から一切変わっていない**（`fieldSize <= 9` と `calPlace < 0.52 && calTanRoi < 85`）。2.5 という定数も、校正勝率10% という条件もコードのどこにも存在しない。

### I. Q3 の前提が事実と異なる

> 「現在は `buildScoredEntry` の中で `horse.simWinRate` があればそれを優先し、なければ従来の能力スコアを使うハイブリッド構成」

そうなっていない。`lib/tanpukuSelection.mjs` に `simWinRate` は 1 箇所も現れない。**構造的欠陥 #1 は診断されただけで、修正されていない。**

### J. 校正の妥当性が「外挿」ではなく「消滅」している

`WIN_CALIBRATION` は **v2.5 が選んだ本命 231 件**にフィットしたもの＝市場に支持された人気馬の集団に条件付けられた写像である。バケット表には生 0.3 未満のサンプルが 0 件。

v3.0 は選定規則を変えたので、**係数が記述していた母集団そのものが存在しなくなった**のに、同じ係数をゲートに使い続けている。さらに傾きが急なため実効的な意味が変質している：

| ゲート | 必要な生 winProb |
| :--- | ---: |
| `isViableCandidate` (calWinProb ≥ 0.12) | 生 ≥ **0.401** |
| 穴馬ゲート @ 3.5倍 | 生 ≥ 0.495 |
| 穴馬ゲート @ 10倍 | 生 ≥ 0.392 |
| 穴馬ゲート @ 20倍 | 生 ≥ 0.336 |
| 穴馬ゲート @ 47.8倍 | 生 ≥ 0.275 |

つまり「勝率12%以上の実力穴馬」を拾っているのではなく、**モデルが生40%前後と評価し市場が10倍以上に置いている馬＝モデルと市場の乖離が最大の馬**を拾っている。事後 holdout で市場に負けているモデルにとって、そこは最も信用できない領域である。class `win` が n=38 → n=222（全体の67%）に膨張したのはその帰結。

### K. テストは緑だが、新しい挙動を一切検証していない

`npm test` 113 件パスは事実。ただし差分はバージョン文字列と `Number.isFinite(winScore)` のみ。`compareWinEntries` の順序も、穴馬ゲートの発火条件もテストされていない。この変更に関して緑であることは証拠にならない。

## 3. Q1〜Q3 への回答

### Q1. 「選定順位の凍結」解除の妥当性

**不変条件を解除するという判断は支持する。実装は支持しない。**

凍結が守っていたのは「検証済みの良い規則」ではなく「人気馬に偏る規則」だった、という指摘は正しく、`rank1 一致率 29.4%` という測定でも裏づけられる。凍結は研究課題として解くべきで、聖域ではない。

ただし今回の実装は、正しく採点すると v2.5 に対してベタ買い −5.4pt・勝負ゲート −17.9pt。加えて **選定規則の変更は校正係数の前提を壊す**（§2-J）ので、この 2 つは一体で動かす必要がある。選定だけ変えて校正を据え置く改変は、どのしきい値を選んでも原理的に正当化できない。

推奨：v3.0 は revert。§1 の診断だけを残し、「選定順位を変える前に、全出走馬ベースで校正をやり直す」順序で再着手する。

### Q2. 低勝率域のロジスティック・デフレ

**移行すべき。ただし理由は「レンジ」ではなく「母集団」。**

現行係数の問題は 10〜15% 帯を潰すことそのものよりも、**選ばれた本命だけにフィットしている**ことにある。区分線形や Isotonic に替えても、同じ 231 件の選択バイアス付きサンプルに当てれば過学習が増えるだけ。

順序としての推奨：
1. **全出走馬**（本命だけでなく）にフィットし直す。サンプルが 327 → 数千に増え、低確率帯に初めて実データが入る。
2. 市場を特徴量として明示的に入れる：`p = sigmoid(a + b·logit(p_model) + c·logit(1/odds))`。レポートが示すとおり市場単独でモデルに勝っているので、これを外生的に無視する設計に合理性がない。
3. Isotonic は 1・2 のあとで、n が十分になってから。231 件・時系列ドリフトあり・選択バイアスありの状態では非単調ノイズを拾う。
4. 人気帯別校正は 1 の下位互換（`logit(1/odds)` を粗く離散化したもの）なので、2 を採るなら不要。

注意点：市場を特徴量に入れた瞬間、**同じフィットから「市場に対するエッジ」を主張できなくなる**。エッジの主張には市場を含まないモデルでの時系列 holdout が別途要る。

### Q3. シミュレータと選定層の完全統合

**これが監査で唯一、実体のある発見。ただし今回の変更より先に、単独で行うべき。**

推奨する順序：
1. `simWinRate` を `buildScoredEntry` に配線する（フラグ付き、選定順位は据え置き）。ここまでで「断絶」は解消し、副作用ゼロで A/B が取れる。
2. `simWinRate` を入力確率として、**全出走馬**で校正を refit（Q2 の 1・2）。
3. **そのあとで初めて**選定順位に手を入れる。しきい値は時系列 holdout の前に凍結する。

懸念点：
- **コスト／レイテンシ**: 週次ルーチンで全レースに 1 万回 MC を事前実行する時間とコスト。ルーチンは GitHub Actions で回っているので、実行時間の上限を先に見積もること。
- **再現性**: MC は確率的なので、**シードをスナップショットに記録**しないと過去予想の監査ができなくなる。`scoringConfigHash` と同じ扱いでシードを持たせる。
- **新しい自由パラメータ**: Softmax 正規化の温度は新たなチューニング対象で、放置すると in-sample で調整される。温度は事前に固定するか、holdout でのみ決める。
- **`score/220` の暗黙の役割**: 現行の分母 220 は事実上のスケール定数として `placeScore` / `valueScore` / 校正係数すべてに効いている。差し替えると下流の定数がすべて意味を変えるので、同時に refit が必要（Q1 と同じ罠）。

## 4. プロセス面の指摘（最も重要な再発防止）

1. **評価スクリプトをコミットする。** `127.2%` / `115.7%` / `114.1%` はリポジトリ内のどのスクリプトからも再生成できない（grep しても監査文書と HANDOVER にしか存在しない）。`HANDOVER.md` に載る数値は `node scripts/<x>.mjs` で再現できるものに限る。
2. **払戻は必ず `result.payouts.tansho` を使う。** スナップショットオッズ×100 は穴馬帯で約2倍の過大評価になる。このルール 1 つで今回の結論が反転する。
3. **しきい値は評価の前に凍結し、時系列 holdout で採点する。** 確定レースへの再選定を "OOS" と呼ばない。
4. **信頼区間を併記する。** n=333・的中17% では 95%CI が ±25pt 開く。点推定だけの ROI 比較は意思決定に使えない。
5. **選定規則を変えたら校正を必ず refit する。** 校正係数は選定規則に条件付けられている。
